## 二、P0：必须修的 Bug（半天内可完成，收益最大）

### 2.1 端口解析：>= 32768 的端口全部失联

**根因**：`MibTcprowOwnerPid.LocalPort` 是 DWORD，端口号按**网络字节序存放在低 16 位**。现行代码：

```csharp
private static int NetworkToHostShort(uint networkShort)
    => (int)IPAddress.NetworkToHostOrder((short)networkShort);   // ← (short) 强转丢符号
```

`(short)` 截断后，字节交换本身是对的，但结果被 **int 接收成正负数判断失误**：>= 0x8000 的端口解析出来是负数，与用户输入的 `port` 比较永远不相等，于是"端口未被占用"——一个假的"空闲"结论，比报错更危险。

**实测（模拟 MIB 行原始值，走现行代码路径）**：

| 输入端口 | 原始 DWORD | 现行代码解析 | 修复后 | 结果 |
|---|---|---|---|---|
| 80 | `0x00005000` | 80 | 80 | ✅ |
| 8080 | `0x0000901F` | 8080 | 8080 | ✅ |
| 32767 | `0x0000FF7F` | 32767 | 32767 | ✅ |
| **32768** | `0x00000080` | **-32768** | 32768 | ❌ 匹配失败 |
| **40000** | `0x0000409C` | **-25536** | 40000 | ❌ 匹配失败 |
| **49152** | `0x000000C0` | **-16384** | 49152 | ❌ 匹配失败 |
| **65535** | `0x0000FFFF` | **-1** | 65535 | ❌ 匹配失败 |

这也解释了为什么你没发现：日常端口 3000 / 3306 / 5173 / 8080 全在 32767 以下，全都正常。而动态端口段（32768–65535）恰恰是"端口冲突排查""临时服务扫尾"最需要覆盖的区间。

**修复（替换 `NetworkToHostShort`）**：

```csharp
/// <summary>
/// 端口按网络字节序存放在 DWORD 低 16 位。禁止用 (short) 强转 —— 会把 >=32768 变成负数。
/// </summary>
private static int NetPortToHost(uint raw)
    => (int)(((raw & 0xFF) << 8) | ((raw >> 8) & 0xFF));
```

调用点两处（line 117 / 118、line 184）同步改名即可。修完顺手加一条单元测试钉死边界，见第五章。

### 2.3 性能：WMI 逐行查询是最大瓶颈

`ResolveProcessInfo()` 里，**每个 PID 单独发一次 WMI 查询**：

```csharp
using var searcher = new ManagementObjectSearcher(
    $"SELECT CommandLine FROM Win32_Process WHERE ProcessId = {info.Pid}");
```

**实测**：`Win32_Process` 带 `CommandLine` 的单次查询 **71.7 ms**（`Get-Process` 仅 11.4 ms，但拿不到命令行）。

推演到真实场景：

| 场景 | 不同 PID 数 | WMI 总耗时 |
|---|---|---|
| 查 8080，1 个 dev server | 1 | ~72 ms（无感） |
| 查 443，多进程复用 | 10 | ~0.7 s |
| 查 80，IIS + 反向代理 + 一堆后端 | 50 | **~3.6 s** |
| 计划中的"全端口总览"（本机 38 个监听 + 数百条 TIME_WAIT） | 100+ | **7 s+，完全不可用** |

配合 2 秒自动刷新和一个几乎无效的 3 秒缓存（刷新到 4 秒时缓存刚被清空，等于每隔一次全量重查），这是持续的 CPU 与磁盘空转。

**修复：命令行改成按需查询 + 全局快照兜底**

1. **主路径**：批量查询只取 `ProcessId, Name`，一次 `Get-Process()` 就够（实测 11 ms 拿全表），**不要碰 CommandLine**。
2. **命令行**：只在用户**选中某一行**时查一次，结果按 PID 缓存。用户一次只会选中一行，成本从 O(N) 降到 O(1)。
3. **兜底**：如果确实需要批量命令行（比如将来的导出功能），用**一次** `SELECT ProcessId, Name, CommandLine FROM Win32_Process` 全量取回再建字典，而不是 N 次单条查询。

```csharp
// 批量进程快照：一次调用解决所有 PID 的名称解析
private static Dictionary<int, string> SnapshotProcessNames()
{
    var map = new Dictionary<int, string>(256);
    foreach (var p in Process.GetProcesses())
    {
        try { map[p.Id] = p.ProcessName; }
        catch { /* 受保护进程，忽略 */ }
        finally { p.Dispose(); }
    }
    return map;
}
```

预期收益：**带大量连接的端口查询从秒级降到 100 ms 以内**，同时为 v2.0 的"全端口总览"功能解锁可行性。

### 2.4 交互：自动刷新会把你的选中行吃掉

`QueryPortAsync()` 每次都是：

```csharp
Connections.Clear();
foreach (var item in unique) Connections.Add(item);
```

`Clear()` 会触发 `SelectionChanged` → `SelectedConnection = null` → "结束进程""复制 PID"按钮变灰。于是勾上自动刷新之后，**你必须在 2 秒内选行并点完按钮**，否则选中自己消失。这是个用户每天都会撞上的体验事故。

**修复：先存选中态，只在数据真变了时重建，重建后恢复选中**

```csharp
var selectedKey = SelectedConnection?.Key;          // Key = $"{Pid}|{Protocol}|{LocalAddress}"

if (!SameAsCurrent(unique))                          // 逐行比对新旧集合
{
    Connections.Clear();
    foreach (var item in unique) Connections.Add(item);
}
SelectedConnection = Connections.FirstOrDefault(c => c.Key == selectedKey);
```

配套在 `ConnectionInfo` 上加个稳定键：

```csharp
public string Key => $"{Pid}|{ProtocolName}|{LocalAddress}";
```

顺带解决另一个隐患：`Clear()` + N 次 `Add` 会触发 N 次集合变更通知，`DataGrid` 逐条重排，连接多时肉眼可见闪烁。真变了才重建，闪烁直接消失。

### 2.5 权限：别让用户自己去猜

当前 `KillSelectedProcessAsync()` 捕获 `UnauthorizedAccessException` 后弹一句"权限不足，请以管理员身份运行"——然后呢？让用户关掉程序、找到 exe、右键"以管理员身份运行"、重新输入端口？这套流程很劝退。

**三件套补齐**：

1. **`app.manifest`**：声明 `requestedExecutionLevel level="asInvoker"`（不强制提权，保持双击即用）、`dpiAwareness = PerMonitorV2`（高分屏不糊）、Windows 10/11 兼容性声明。
2. **启动时检测**：`new WindowsPrincipal(WindowsIdentity.GetCurrent()).IsInRole(WindowsBuiltInRole.Administrator)`，状态栏显示"普通权限 / 管理员"，普通权限时给个黄色提示条。
3. **一键提权重启**：

```csharp
var psi = new ProcessStartInfo(Environment.ProcessPath!)
{
    UseShellExecute = true,
    Verb = "runas"           // 弹 UAC
};
Process.Start(psi);
Application.Current.Shutdown();
```

## 三、P1：能力补齐（决定这工具是"能用"还是"爱用"）

### 3.1 IPv6 / 双栈支持（现有功能的硬缺口）

所有枚举都写死 `AF_INET = 2`。而现代开发栈里，Node、Vite、Python `http.server`、Java 默认监听 `::`（双栈），在 **IPv6 表**里才会出现：

```
TCP    [::]:5173    [::]:0    LISTENING    12345
```

只查 IPv4 表的结果就是：浏览器能打开 `localhost:5173`，工具却说"端口未被占用"。**这是最容易被用户判定为"这工具不准"的场景，一次就够卸载。**

修复要点（结构体对齐是关键，错一个字段全部数据错位）：

```csharp
private const int AF_INET6 = 23;

[StructLayout(LayoutKind.Sequential)]
private struct MibTcp6RowOwnerPid
{
    [MarshalAs(UnmanagedType.ByValArray, SizeConst = 16)] public byte[] LocalAddr;
    public uint LocalScopeId;
    public uint LocalPort;
    [MarshalAs(UnmanagedType.ByValArray, SizeConst = 16)] public byte[] RemoteAddr;
    public uint RemoteScopeId;
    public uint RemotePort;
    public uint State;
    public uint OwningPid;
}   // 总长 56 字节，务必用 Marshal.SizeOf 断言校验
```

UDP 侧对应 `MibUdp6RowOwnerPid`。IPv6 地址转字符串用 `new IPAddress(addrBytes).ToString()`，注意处理 `::` 与 scope-id（`fe80::1%12`）。

> 优化项：一次查询同时枚举 IPv4 + IPv6，结果按 `(Pid, Protocol, LocalAddress)` 去重。当前 `GroupBy` 已有去重逻辑，直接复用。

### 3.2 全端口总览：真正的"杀手功能"

现在必须**先知道端口号**才能查。但用户真实场景往往是反的：

> "我这个 node 进程到底占了哪几个端口？"
> "8000 到 9000 这段被谁吃光了？"
> "哪个进程在偷偷监听 0.0.0.0？"

建议加一个**视图切换**（单端口查询 / 全端口总览）：

- 左侧（或顶部）按**进程**聚合，右侧展开该进程的所有连接
- 支持按进程名、端口、状态过滤
- 默认只显示 LISTENING + ESTABLISHED，过滤掉 TIME_WAIT 噪声（本机 38 个监听，TIME_WAIT 可能有几百条）

这需要 2.3 的性能修复作为前提——否则一打开就转圈 7 秒。

### 3.3 其他高价值小功能

| 功能 | 为什么值得做 | 成本 |
|---|---|---|
| **端口段扫描**（8000-8100） | 找"哪个端口空着"比找"谁占了"更常用 | 低（循环 + 合并结果） |
| **导出 CSV / JSON** | 排查问题时发同事，比截图专业 | 低 |
| **复制为 netstat 行** / 复制完整信息 | 粘到工单/聊天里 | 极低 |
| **右键菜单**（结束/复制/打开文件位置/在浏览器打开） | DataGrid 没右键菜单，用户第一反应就是右键 | 低 |
| **常用端口预设**（3000/3306/5173/6379/8080） | 省掉每天重复输入 | 极低 |
| **优雅结束**：先 `CloseMainWindow()`，3 秒不退再 `Kill()` | `Kill(true)` 强杀 dev server 会丢未保存状态 | 低 |
| **系统进程保护名单** | 详见 3.4 | 极低 |
| **窗口位置/大小记忆 + 单实例** | 小工具的基本礼貌 | 低 |
| **查询历史（最近 10 个端口）** | 排查时反复查同几个端口 | 极低 |

### 3.4 安全：`Kill(true)` 需要一道闸

```csharp
process.Kill(true);   // 连子进程树一起杀
```

两个风险：

1. **`true` = 杀整棵树**。杀一个启动器进程，可能连带干掉它托管的服务；杀 `explorer.exe` 会连带桌面所有窗口进程。
2. **没有保护名单**。手动杀 `csrss.exe` / `wininit.exe` / `lsass.exe` 的后果是立即蓝屏或强制重启，这不是夸张。

**建议**：

```csharp
private static readonly HashSet<string> Protected = new(StringComparer.OrdinalIgnoreCase)
{
    "system", "idle", "smss", "csrss", "wininit", "winlogon", "services",
    "lsass", "svchost", "dwm", "fontdrvhost", "spoolsv", "explorer"
};
```

- 命中名单 → 按钮禁用 + 提示"系统关键进程，已禁止操作"
- 默认**只杀主进程**，`Kill(true)` 降级为高级选项（Shift 点击 / 设置里勾选）
- PID 4（System）、PID 0（Idle）直接拦住

### 4.4 代码细节（顺手改掉）

- `MainWindow.xaml.cs` 里手工转发 `SelectionChanged` → 直接在 XAML 绑 `SelectedItem="{Binding SelectedConnection}"`，code-behind 少 12 行
- `((RelayCommand)CheckPortCommand).RaiseCanExecuteChanged()` 这处强转，一旦换成别的 `ICommand` 实现就运行时炸。改 `CommandManager.RequerySuggested` 或把属性声明成 `RelayCommand` 类型

## 五、架构演进方向

现在的 `NativeNetworkService` 是个 `static` 大杂烩：P/Invoke + 结构体解析 + 进程解析 + 缓存全塞一起（299 行）。建议按职责切开：

```
MainViewModel
   ↓ 依赖接口
IConnectionProvider ─┬─ IpHelperProvider      (主路径，P/Invoke，IPv4+IPv6)
                     └─ NetstatFallbackProvider (可选，权限/兼容性兜底)
IProcessInfoProvider ─┬─ ProcessSnapshotProvider  (批量名称，11ms)
                      └─ CommandLineProvider      (按需单查，选中时触发)
IDialogService / IClipboardService   (可替换 → 可测试)
```

好处：IPv6 单独加一个 provider、命令行查询按需替换实现（未来上 `NtQueryInformationProcess` 读 PEB 可以做到 1ms 级）、测试全部可 mock。

**关于命令行的终极方案**（可选，不是必须）：`NtQueryInformationProcess` + `ReadProcessMemory` 读 PEB 拿 `ProcessParameters.CommandLine`，单次约 0.1 ms，比 WMI 快两个数量级。代价是代码复杂度陡增（32/64 位、WoW64 兼容、异常处理一堆）。**建议先用"按需查询"策略，真不够用再上**——别为了性能引入一个自己都不敢改的 P/Invoke 黑洞。

**核心指标（v2.0 目标）**：

- 100 条连接首次查询 **< 300 ms**（当前约 7 s 量级）
- 自动刷新（2 s）CPU 占用 **< 2%**
- 端口 1–65535 全覆盖，IPv4/IPv6 双栈
- 内存 **< 80 MB**
- 单元测试覆盖端口解析 / 去重 / 保护名单三类关键逻辑

## 七、优先级建议（如果只想动一天）

按"投入产出比"从高到低，天花板最低的活先干：

1. **端口解析 Bug**（10 分钟，修一个真故障）
2. **`.slnx` + README**（5 分钟，让项目能被别人构建）
3. **自动刷新丢选中**（30 分钟，每天都疼）
4. **WMI → 批量快照**（2 小时，性能提升一个数量级）
5. **manifest + 一键提权**（1 小时，解决真实卡点）
6. **系统进程保护名单**（20 分钟，防蓝屏）

这 6 项加起来半个工作日，工具从"能用"直接跳到"靠得住"。剩下的 UI 现代化和全端口总览是加分项，可以慢慢来。
